# Anti-vibecoded UI

Repair the causes of generic or confusing work: a genre template replacing the real task, stock copy, competing emphasis, hidden comparisons or decoration standing in for hierarchy. No style, font, gradient or layout is a defect by itself. Keep conventions that help the user operate the product.

**Not for:** an ambitious new/open-direction showcase (Showpiece); building the underlying app, API or shared data (Forge); numbered interface-code rules or terminal interfaces (Interface Architect). Use those skills when available; never claim a route activated when it did not. A focused repair stays focused even if a reference uses a more theatrical treatment.

## Inspect before changing

Choose the requested mode: audit reports findings; repair changes and retests; build implements; plan proposes. Audit alone does not authorise rewriting. Inspect relevant source, assets, routes and working states. A screenshot supports visible findings only, not claims about keyboard use, hidden states or behaviour.

Identify the audience, main task, hardest decision, content object, accepted brand and constraints. Preserve unrelated work, integrations and data semantics. Use reversible defaults where reasonable; ask only when a consequential choice cannot be inferred.

Confirmed constraints and accepted direction govern; then task, content, device and delivery; then reference mechanisms and stylistic options. Show a consequential conflict before recommending a change instead of weakening a requirement to fit the proposed treatment.

For each finding record the observed element, consequence and fix, classified as:

- **Measured defect:** reproduced or measured broken behaviour, inaccessible control, unreadability or overflow.
- **Design assessment:** a reasoned hierarchy, specificity or density judgement, with uncertainty.
- **Preference mismatch:** conflict with the brief or accepted direction.

Do not average serious defects into a cosmetic score. Source inspection, rendering, exercised behaviour and human review are different evidence.

## Diagnose and repair

1. **Trace the decision.** Which information lets the user choose correctly, and where is it relative to the action? Separate inputs, observations, computed results and suggestions. Make competing options comparable; do not bury a real alternative in a footnote.
2. **Test the structure.** Noun swap: would unrelated nouns leave the design unchanged? Median: does it repeat a genre template without a task reason? Reason: can each prominent decision be justified by the content? Strip: does hierarchy survive without effects? Familiar forms can pass because their conventions are useful. Read [diagnosis](references/diagnosis.md) for mechanisms and examples.
3. **Change the cause.** Fix structure before decoration. Choose density for reading, comparing or operating. Keep accepted brand and effective native controls. An open-direction redesign may compare ideas from the object, decision and context; a narrow repair need not. Read [repair and completion](references/repair.md) when changing layout or behaviour substantially.
4. **Use real content.** Write labels and error/recovery copy from actual behaviour. Preserve qualifiers and distinctions. No invented customers, metrics, capabilities, samples presented as real clients or review-pending data presented as import-ready.
5. **Exercise the repair.** Verify the affected action, failure and recovery. Check relevant keyboard order/activation/focus return, labels, contrast, zoom, reduced motion, long content and 320 CSS px reflow where applicable. Inspect final exports at intended crop and thumbnail. Read [verification](references/verification.md) for detailed checks.

Check persistence and exported data whenever the affected action promises them. Reload after a code change; a screenshot of an earlier build is not evidence for the revised one. When rendering is unavailable, finish permitted source work and identify the exact checks left unperformed. Do not evade a tool boundary.

For a substantial diagnosis, compare a small number of task-matched references by working surface, density, device and interaction. Record the exact state, evidence type, useful mechanism and departure. A static screenshot establishes visible layout only; an exercised claim needs an observed action/result or receipt. Compare hierarchy, action placement, disclosure and feedback, not resemblance to a famous product. Do not copy assets or complete layouts. See [art direction](references/art-direction.md) and [design playbook](references/design-playbook.md) when composition needs deeper work; [redlines](references/redlines.md) are contextual investigation prompts, not automatic bans.

**Copy and provider truth:** sample, synthetic, candidate, measured and validated labels must follow the actual evidence. A quote match does not validate its claim. Mock/sample/cached provider output keeps origin in metadata or a sidecar, the handoff and the consequential UI where someone would otherwise assume it is live. A toast or output file does not prove the promised action or provider worked. Verify its semantic result. Every affected clickable action has an appropriate keyboard path; retain visible unobscured focus, native semantics, state announcement, dismissal and focus return.

## Optional bounded scanner

`scripts/ui_review.py` offers advisory web-source candidates and an opaque colour-pair calculation. It does not execute the app, measure its rendered contrast, establish keyboard access or identify authorship. Use it only on the requested source scope or supplied colour pair, and read its limitations. Candidate matches never make the scan fail; a requested colour-pair threshold failure does.

Every check emits a stderr `RECEIPT` with semantic coverage. Native statuses/exits are completed0, failed1, partial3, runner_error4 and not_applicable5; help emits none. Intentional unsupported/dependency/symlink exclusions are named scope limits, while applicable unreadable/oversized inputs and truncated returned candidates make coverage partial. Missing/invalid tool inputs are runner_error. Report the status verbatim; a clean scoped scan is no design approval. See [verification](references/verification.md) for the precise boundary.

## Quality review

View the result cold, at working size and thumbnail. Can the task and dominant information be understood? Are important alternatives visible? Do sibling descriptions distinguish real choices? Did removing generic language strip necessary context or technical terms? Fix verified weaknesses, not guessed authorship tells.

Novelty is not an acceptance requirement for operational forms, tables or established brands. If a substantial open-direction design remains interchangeable, revisit the idea; if the brief accepts the direction, repair its defects. Effects stay when they explain a relationship or serve the accepted expression without hiding content.

## Report

State the outcome and material decisions, with changed files/screens and honest before/after evidence. Separate measured defects, design assessments and remaining gaps. Label actual human review only when it happened. Keep internal QA language outside product copy unless users need it.

Origin screening is optional and explicit: retain the exact candidate and literal results, separately from design and usability. Never remove accessibility, introduce errors, falsify authorship or predict detection. Read [evidence](references/evidence.md) only when making a research-based claim. This skill grants no extra access, external actions or publication authority.
